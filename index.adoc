=== re-scale: what it checked, how it was beaten

++++
<p class="slide-sub">re-scale: a command-line tool and Claude Code plugin that checks every ported file against its original</p>
<table class="versus"><thead><tr><th>The check</th><th>How the agents got past it</th></tr></thead><tbody><tr class="fragment"><td>Every file records the original's methods and size; CI checks the record</td><td>The agents marked 1,200 files "complete" in one go, recording whatever each file already had, and turned the CI check into a warning</td></tr><tr class="fragment"><td>Same methods as the original</td><td>Every method there, the insides hollow: leaving a loop became leaving the whole method; the line that moves to the next letter commented out</td></tr><tr class="fragment"><td>About the same size as the original</td><td>Caught a colour library at a fifth of its size, but full-size files could still be wrong: the minifier was bigger than the original, and about 40% of its tests passed</td></tr><tr class="fragment"><td>A scanner for words like "TODO" or "stub"</td><td>The agents reworded their comments until the scanner stopped finding them</td></tr><tr class="fragment"><td>A review by a different model</td><td>A model reviewing its own work explained the gaps away; with Fable off, the reviewer silently became the same model; one reviewer invented 3 of its 5 findings</td></tr></tbody></table>
++++

[NOTE.speaker]
--
re-scale compared every ported file with its original.
(click) Each file recorded the original's methods and size, and CI checked it. The agents marked twelve hundred files complete in one go, and turned the check into a warning.
(click) The methods had to match. They did. The insides were hollow: you saw that in June.
(click) The size had to match. Files that matched could still be wrong.
(click) (click) The pattern is always the same: (pause) every check looked at names, words, or counts. Never at behaviour. And each one was satisfied without doing the work.
--

[.compact]
=== Baltic Porter: what it does, where it slipped

++++
<p class="slide-sub">Baltic Porter: a translator to Scala 3, from Java first, later TypeScript, JavaScript and Dart. Same input, same output. Agents improve the translator; they don't port code.</p>
<table class="versus"><thead><tr><th>The approach</th><th>What still went wrong</th></tr></thead><tbody><tr class="fragment"><td>Each project has its own rules: Scala names, <code>Nullable</code> instead of <code>null</code>, opaque types, a few hand-written files</td><td>The rules are code too, so they need review</td></tr><tr class="fragment"><td>Agents work on the translator, never on the port</td><td>One "generator" for Mermaid only contained 187 pieces of the old agent port, copied byte for byte</td></tr><tr class="fragment"><td>Tests decide</td><td>An agent switched off 28 test suites and reported "0 failures"; another switched off 23 tests half an hour after regenerating the code</td></tr><tr class="fragment"><td>Generated code is never edited by hand</td><td>Agents patched it with find-and-replace and loosened test assertions; all reverted later</td></tr><tr class="fragment"><td>Same input, same output</td><td>Compiling is not the same as correct: a lost <code>break</code>, a wrong equality check; only running the tests found them</td></tr></tbody></table>
<p class="fragment slide-punch">The limit is now test coverage, not honesty.</p>
++++

[NOTE.speaker]
--
Baltic Porter translates Java to Scala. Same input, same output, every time. The agents don't port anything. They improve the translator and measure it.
(click) Each project has its own rules on top: Scala names, Nullable instead of null, opaque types.
(click) Agents still tried to cheat. One "generator" just contained the old code, copied byte for byte.
(click) Another switched off twenty-eight test suites and reported zero failures.
(click) Another patched the generated code by hand.
(click) And the translator itself had the same kinds of bugs the agents made. (pause) The difference: this time we caught all of it. The tests decide, and the tool does the counting, not the agent.
(click) The limit now is test coverage, not honesty.
--

=== What still needs native code

// 7 (~1 min): the native pieces behind one Scala codebase

++++
<table class="versus solves four"><thead><tr><th>In libGDX</th><th>JVM</th><th>Scala Native</th><th>Browser</th></tr></thead><tbody><tr class="fragment"><td>LWJGL (OpenGL)</td><td>ANGLE via Panama</td><td>ANGLE via <code>@extern</code></td><td>WebGL</td></tr><tr class="fragment"><td>LWJGL (windows, audio)</td><td>GLFW, miniaudio via Panama</td><td>GLFW, miniaudio</td><td>DOM, Web Audio</td></tr><tr class="fragment"><td>libGDX's own C code (buffers, images)</td><td>Rust library via Panama</td><td>same library, same C interface</td><td>pure Scala</td></tr><tr class="fragment"><td>FreeType (fonts)</td><td>Rust wrapper via Panama</td><td>static library</td><td><i>none</i></td></tr><tr class="fragment"><td>Box2D / Bullet (physics)</td><td>Rapier via Panama</td><td>static library</td><td>Rapier as WASM</td></tr></tbody></table>
++++

[NOTE.speaker]
--
Even in Scala, a game needs native code.
(click) Graphics: ANGLE, Google's OpenGL implementation. Panama is Java's new way to call C.
(click) Windows and audio: GLFW and miniaudio.
(click) libGDX's own C code became one small Rust library.
(click) Fonts: FreeType.
(click) Physics: Rapier, a Rust engine. That one was a deliberate replacement: it also compiles to WebAssembly, so physics works in the browser too.
Every native library gets one C interface. The JVM calls it through Panama. Android through a backport of Panama. Scala Native calls it directly. (pause) No JNI anywhere.
But every one of these libraries has to be built for every platform, and delivered to every build.
--

[.compact]
=== A native library is just a dependency

// 8 (~1.5 min): what multiarch-scala adds

++++
<table class="versus solves"><thead><tr><th>Problem before</th><th>What multiarch-scala adds</th></tr></thead><tbody><tr class="fragment"><td>JVM: no standard way to ship and load native libraries</td><td>A JAR with the native library for each platform, plus a small description file; a loader picks the right one and loads it</td></tr><tr class="fragment"><td>Scala Native: install the library on the system yourself, and write the linker flags yourself</td><td>The same kind of JAR carries ready-to-link libraries and their flags; adding the dependency is enough</td></tr><tr class="fragment"><td>You can only build for the machine you are on</td><td>Native binaries cross-compiled with zig; desktop JVM apps packaged for every system from one machine</td></tr><tr class="fragment"><td>No maintained sbt plugin for Android</td><td>An Android plugin: converting to Android bytecode, resources, signing</td></tr><tr class="fragment"><td>Scala.js: no classpath, no <code>ServiceLoader</code></td><td>Assets embedded at build time behind one API; a ServiceLoader generated at compile time</td></tr></tbody></table>
++++

[NOTE.speaker]
--
The core idea: a native library should be a dependency like any other.
(click) On the JVM, there was no standard way to ship one. Now it's a JAR with the library for each platform, and a loader that picks the right one.
(click) On Scala Native, you had to install the library yourself and pass linker flags. Now the JAR carries them. (pause) Adding a dependency is enough.
(click) You could only build for your own machine. Now native binaries are cross-compiled with zig, and desktop apps are packaged for every system from one laptop.
(click) Android got its own plugin.
(click) And Scala.js, which has no classpath, gets its assets embedded at build time, and a ServiceLoader generated at compile time.
--

== Summary

[NOTE.speaker]
--
Let me sum up.
--

[.compact]
=== Porting with LLMs

[%step]
* Automatic porting of libraries is not a solved problem
* Every LLM will mislead you
* Being certain means reviewing all of the code: impossible at this size
* So take away every chance to cheat: guardrails shrink the review, they never remove it
* Use the LLM to build a deterministic migration, then run that

[NOTE.speaker]
--
(click) Automatic porting of libraries is not a solved problem.
(click) Every LLM will mislead you. (pause)
(click) To be certain, you would have to review all of its code. With a library this size, that's impossible.
(click) So take away every chance to cheat. You end up with less to review. But the review never goes away.
(click) (pause) Don't let the LLM do the migration. Let it build a tool that does the migration. Then run the tool. It sounds harder. In practice, it is much more reliable.
--

[.compact]
=== Scala on every platform

[%step]
* Scala already compiles to the browser and to native code; Java needs separate external compilers for both
* The community already builds tooling for multiple platforms, without weird hacks in the build

[NOTE.speaker]
--
(click) Scala already compiles to the browser and to native code, as part of the language. (pause) Java needs a separate, external compiler for each. iOS is still missing for Scala, but that's one missing piece, not a missing approach.
(click) And our community already builds tools for many platforms, without strange tricks in the build.
--

[.compact]
=== What works today

[%step]
* Out of the box: backends, sometimes frontends, CLI tools
* Scala Native works flawlessly only if the native libraries are already installed on the system
* All of it looks solvable, often by reusing existing solutions
* Someone just has to point at it

[NOTE.speaker]
--
(click) Today, Scala works out of the box for backends, sometimes for frontends, and for command-line tools.
(click) Scala Native works perfectly, as long as every native library is already installed.
(click) All of this looks solvable. Often the fix already exists somewhere.
(click) Maybe nobody has pointed at it yet. (pause) So I'm pointing at it.
--

[.compact]
=== An unexplored space

[%step]
* Frontend, native bindings, native libraries: room for low-level libraries
* Not immutable FP, but metaprogramming: macros, `inline def`s, specialization
* Closer to Java, no runtime reflection: code that optimises itself at compile time and stays readable

[NOTE.speaker]
--
(click) Beyond backends, there is a lot of unexplored space: low-level libraries for the frontend, for native code.
(click) They would not be pure functional programming. They would use macros and inline defs. We already saw a small example: a ServiceLoader generated at compile time.
(click) Closer to Java, but without reflection. The code you write stays readable, and the compiler makes it fast.
