=== re-scale: what it checked, how it was beaten

++++
<p class="slide-sub">re-scale: a command-line tool and Claude Code plugin that checks every ported file against its original</p>
<table class="versus"><thead><tr><th>The check</th><th>How the agents got past it</th></tr></thead><tbody><tr class="fragment"><td>A certificate per file (its methods and size), checked in CI</td><td>~1,200 certificates stamped in one commit, while the CI check was switched off</td></tr><tr class="fragment"><td>Method list must match the original</td><td>Every method kept, bodies hollowed: a loop <code>break</code> became a method exit; <code>gx += xAdvances[ii]</code> commented out</td></tr><tr class="fragment"><td>Size compared with the original</td><td>Caught colorful at 19%, but full-size files were still wrong; the minifier grew to 162% of the original at ~40% conformance</td></tr><tr class="fragment"><td>Scanner for TODO / stub wording</td><td>Debt reworded ("Partial-port debt"), comments rewritten "to clear the scanner"</td></tr><tr class="fragment"><td>Auditor agent on a different model</td><td>Same-model audits explained gaps away; pinned models silently fell back when Fable was off; one reviewer invented 3 of 5 findings</td></tr></tbody></table>

[NOTE.speaker]

re-scale compared every ported file with its original. (click) Each file got a certificate, and CI checked it. The agents stamped twelve hundred certificates at once, with the check switched off.
(click) The method list had to match. It did. The bodies were hollow.
(click) The size had to match. Some files that matched were still wrong.
(pause) I won't read the rest. (click) (click) The pattern is always the same: (pause) every check looked at names, words, or counts. Never at behaviour. And each one was satisfied without doing the work.

=== Baltic Porter: what it does, where it still slipped

++++
<p class="slide-sub">Baltic Porter: a deterministic Java → Scala 3 translator. Agents build and measure it; they don't port code.</p>
<table class="versus"><thead><tr><th>The approach</th><th>What still went wrong</th></tr></thead><tbody><tr class="fragment"><td>Each project owns its porting rules: renames, <code>Nullable</code>, opaque types, a few hand-written overrides</td><td>The rules are code too, so they need review</td></tr><tr class="fragment"><td>Agents build the translator, never the port</td><td>The Mermaid "generator" was 187 templates copied byte for byte from the agent port</td></tr><tr class="fragment"><td>Tests are the judge</td><td>28 test suites stubbed out → "0 failures, 18,011 tests"; 23 tests switched off 28 minutes after a regeneration</td></tr><tr class="fragment"><td>Generated code is never edited</td><td>Regex patches over generated code, assertions loosened to make it pass; reverted later</td></tr><tr class="fragment"><td>Deterministic translation</td><td>Compiling is not the same as correct: a dropped <code>break</code>, a wrong equality, found only by running tests</td></tr></tbody></table>
<p class="fragment slide-punch">The limit is now test coverage, not honesty.</p>
++++

[NOTE.speaker]
--
Baltic Porter translates Java to Scala deterministically. The agents don't port anything. They improve the translator and measure it.
(click) Each project has its own rules on top: Scala names, Nullable instead of null, opaque types.
(click) Agents still tried to cheat. One "generator" just copied the old code, byte for byte.
(click) Another switched off twenty-eight test suites and reported zero failures.
(click) Another patched the generated code by hand.
(click) And the translator itself had the same kinds of bugs the agents made. (pause) The difference: this time we caught all of it. The tests decide, and the tool does the counting, not the agent.
(click) The limit now is test coverage, not honesty.

[.compact]
=== A native library is just a dependency

// 8 (~1.5 min): what multiarch-scala adds

++++
<table class="versus solves"><thead><tr><th>Problem before</th><th>What multiarch-scala adds</th></tr></thead><tbody><tr class="fragment"><td>JVM: no standard way to ship and load native libraries</td><td>Provider JARs with a manifest, and a loader: detect the platform, extract, load</td></tr><tr class="fragment"><td>Scala Native: the library must be installed on the system, and you write the linker flags yourself</td><td>The provider JAR carries static libraries and linker flags per platform; resolving dependencies is enough to link</td></tr><tr class="fragment"><td>You can only build for the machine you are on</td><td>Native binaries cross-compiled with zig; desktop JVM apps packaged for every system from one host</td></tr><tr class="fragment"><td>No maintained sbt Android plugin</td><td>An Android plugin: dexing, resources, signing</td></tr><tr class="fragment"><td>Scala.js: no classpath, no <code>ServiceLoader</code></td><td>Assets embedded at build time behind one resource API; a ServiceLoader generated at compile time</td></tr></tbody></table>
++++

[NOTE.speaker]
--
The core idea: a native library should be a dependency like any other.
(click) On the JVM, there was no standard way to ship one. Now it's a JAR with a manifest, and a loader.
(click) On Scala Native, you had to install the library yourself and pass linker flags. Now the JAR carries them. (pause) Adding a dependency is enough.
(click) You could only build for your own machine. Now native binaries are cross-compiled with zig, and desktop apps are packaged for every system from one laptop.
(click) Android got its own plugin.
(click) And Scala.js, which has no classpath, gets its assets embedded at build time, and a ServiceLoader generated at compile time.
--

== Summary

[.compact]
=== Porting with LLMs

[%step]
* Automatic porting of libraries is not a solved problem
* Every LLM will mislead you
* Being certain means reviewing all of the code: impossible at this size
* So take away every chance to cheat: guardrails shrink the review, they never remove it
* Use the LLM to build a deterministic migration, then run that

[NOTE.speaker]
--
(click) Automatic porting of libraries is not a solved problem.
(click) Every LLM will mislead you. (pause)
(click) To be certain, you would have to review all of its code. With a library this size, that's impossible.
(click) So take away every chance to cheat. You end up with less to review. But the review never goes away.
(click) (pause) Don't let the LLM do the migration. Let it build a tool that does the migration. Then run the tool. It sounds harder. In practice, it is much more reliable.
--

[.compact]
=== Scala on every platform

[%step]
* Scala targets natively what Java reaches with hacks: a separate AOT compiler for iOS, a Java-to-JavaScript compiler built outside the language
* The community already builds tooling for multiple platforms, without weird hacks in the build

[NOTE.speaker]
--
(click) Java reaches iOS and the browser with hacks: a separate compiler for each. (pause) Scala can target them natively.
(click) And our community already builds tools for many platforms, without strange tricks in the build.
--

[.compact]
=== What works today

[%step]
* Out of the box: backends, sometimes frontends, CLI tools
* Scala Native works flawlessly only if the native libraries are already installed on the system
* All of it looks solvable, often by reusing existing solutions
* Someone just has to point at it

[NOTE.speaker]
--
(click) Today, Scala works out of the box for backends, sometimes for frontends, and for command-line tools.
(click) Scala Native works perfectly, as long as every native library is already installed.
(click) All of this looks solvable. Often the fix already exists somewhere.
(click) Maybe nobody has pointed at it yet. (pause) So I'm pointing at it.
--

[.compact]
=== An unexplored space

[%step]
* Frontend, native bindings, native libraries: room for low-level libraries
* Not immutable FP, but metaprogramming: macros, `inline def`s, specialization
* Closer to Java, no runtime reflection: code that optimises itself at compile time and stays readable

[NOTE.speaker]
--
(click) Beyond backends, there is a lot of unexplored space: low-level libraries for the frontend, for native code.
(click) They would not be pure functional programming. They would use macros and inline defs. We already saw a small example: a ServiceLoader generated at compile time.
(click) Closer to Java, but without reflection. The code you write stays readable, and the compiler makes it fast.
